# myCode 未来功能改造与企业级架构升级方案

> 文档定位：面向开发团队的未来功能规划、架构演进和企业级改造说明
> 当前基线：现有 Agent Loop、工具系统、权限、MCP、上下文/记忆、Skill、Hook、Sub Agent、Worktree 和 Team 能力
> 配套文档：`doc/agent-enterprise-upgrade-roadmap.md` 负责工程欠账和分阶段基础设施路线，本文件负责未来功能和产品架构演进。

## 1. 总体判断

当前项目已经从“能调用大模型的终端工具”发展成了具备 Agent Loop、流式协议、工具执行、权限审批、上下文压缩、项目记忆、Skill、Hook、子 Agent 和 Team 编排能力的本地 Agent 平台雏形。

下一阶段不能只继续增加更多工具或 Prompt。真正的升级方向是把 Agent 从一个绑定 CLI 进程的执行器，提升为企业可以管理、审计、扩展和横向扩容的任务平台：

```text
本地 CLI Agent
    -> 模块化单体 Agent
    -> 可恢复的 Run Runtime
    -> 控制面 + 数据面
    -> 多租户分布式 Agent 平台
```

目标平台需要同时满足四类要求：

1. **功能完整：** 用户可以创建任务、持续观察、暂停、审批、恢复、重试和复盘。
2. **工程可靠：** 节点、模型、工具、网络或消息失败时，任务不会静默丢失或进入不可恢复状态。
3. **企业治理：** 用户、组织、项目、权限、成本、数据保留和审计可管理。
4. **架构可演进：** 本地模式、服务模式和分布式模式共享领域模型，不出现三套行为实现。

## 2. 当前基础与架构约束

| --- | --- | --- |

| MCP | `src/mycode/mcp/` | stdio、Streamable HTTP、远端工具发现 |
| 上下文压缩 | `src/mycode/compact/` | 归档、摘要、预算估算和熔断 |

| Team 协作 | `src/mycode/team/` | Lead/member、事件记录、角色队列、确认和重试 |
| 代码隔离 | `src/mycode/worktree/` | Worktree 创建、保护、清理和状态检查 |

### 2.2 必须保留的架构约束

- Agent Loop 不直接理解 HTTP、数据库或消息队列协议，使用端口接口。
- TUI、CLI、未来 IDE 和 Web 客户端只消费稳定的 Run/Event 契约。
- 工具执行和模型调用都必须返回结构化结果，不能依赖异常文本作为业务协议。
- 事件是可恢复事实，通知只负责唤醒，不是唯一数据来源。
- 本地 file-backed 实现保留为开发适配器，生产环境切换到共享存储和事件总线。
- 所有长任务都要能够暂停、恢复、取消和重试；不能把恢复逻辑藏在某个进程的内存变量中。

## 3. 未来功能地图

未来功能按四个层次推进：

```text
用户体验层：客户端、项目、任务、审批、报告、协作
业务能力层：Agent、Team、Workflow、Memory、Tool、Model
平台治理层：身份、租户、权限、配额、审计、计费、评测
基础设施层：API、数据库、事件总线、对象存储、Worker、Sandbox、观测
```

### 3.1 F01：统一任务中心（Run Center）

**用户价值：** 用户可以创建一次可追踪的 Agent Run，并查看当前阶段、消耗、工具调用、审批等待、失败原因和最终产物，而不是只能在终端中等待一段连续输出。

**当前基础：** `AgentLoop` 已有轮次和终止事件，`session.py` 已有会话记录，Team 已有事件和状态。

**目标功能：**

- 创建、查询、取消、暂停、恢复、重试和归档 Run。
- 支持交互式 Run、后台 Run、定时 Run、Webhook 触发 Run 和批量 Run。
- Run 下分解 WorkItem、Attempt、ToolCall、Approval 和 Artifact。
- 支持事件 cursor，客户端断线后从指定位置继续接收。
- 支持父子 Run，Sub Agent 和 Team 成员成为可追踪的子工作项。
- 支持运行摘要、失败诊断、成本统计和产物索引。

**企业级升级：**

- Run 状态持久化到 PostgreSQL，事件进入事件账本。
- 使用幂等键防止客户端重复创建任务。
- 通过租约和心跳支持 Worker 接管。
- 通过租户配额、优先级和队列隔离控制资源。
- 使用审计事件记录创建者、审批者、执行者和最终状态。

**建议模块：** 新增 `src/mycode/run/`、`src/mycode/api/runs.py`、`src/mycode/runtime/checkpoints.py`。

**验收结果：** Worker 被杀后，另一个 Worker 能从最近 checkpoint 恢复；客户端断线重连后不会丢事件，也不会重复执行已确认的副作用。

### 3.2 F02：企业工作区与项目管理

**用户价值：** 将当前隐含的工作目录升级为可管理的组织、项目和环境，用户可以绑定代码仓库、分支、构建环境、工具白名单和项目记忆。

**目标功能：**

- 组织、租户、项目、环境和代码仓库绑定。
- 项目级 Agent 指令、Skill、Hook、Memory、Model 和 Tool Policy。
- 开发、测试、预发布和生产环境的配置分层。
- 项目成员、服务账号和外部协作者管理。
- 项目模板、初始化脚本和环境健康检查。
- 变更前后工作区快照、Artifact 和差异报告。

**企业级升级：**

- 所有项目资源带 `tenant_id` 和 `project_id`，存储层执行强制隔离。
- 仓库凭据使用短期 token，不能写入项目文件或普通日志。
- 项目策略有版本号，Run 记录使用的策略版本。
- 生产环境默认禁止自动写入，必须进入审批流程。

**建议模块：** `src/mycode/workspace/` 扩展为 Workspace Service；新增 `project/`、`environment/`、`repository/` 领域模块。

**验收结果：** 同一用户可以管理多个项目；跨租户、跨项目访问在 API、数据库、对象存储、缓存和事件层都被拒绝。

### 3.3 F03：身份、租户与企业权限中心

**用户价值：** 企业可以使用统一登录、组织权限和项目权限，而不是依赖本地 YAML 规则和环境变量。

**目标功能：**

- OIDC/OAuth2 登录、服务账号、API token 和短期 worker token。
- 组织、团队、项目、角色和资源层级。
- RBAC 控制基础操作，ABAC 控制环境、工具、仓库和数据范围。
- 权限申请、审批、临时授权、过期和撤销。
- 策略模拟、策略版本比较和授权失败解释。

**企业级升级：**

- 默认拒绝，系统安全底线不能被租户策略覆盖。
- 每次授权判定记录主体、资源、动作、策略版本和结果。
- API、事件消费者、MCP connector 和 Sandbox worker 都重新校验服务身份。
- 对高风险操作支持双人审批和四眼原则。

**建议模块：** `src/mycode/identity/`、`src/mycode/policy/`、`src/mycode/audit/`。

**验收结果：** 用户失去项目权限后，正在等待的任务不能继续获得新的高风险工具授权；权限变化可以在审计中还原。

### 3.4 F04：模型网关与智能路由

**用户价值：** 用户不需要关心具体模型供应商，平台可以根据任务类型、延迟、质量、成本和合规要求选择模型。

**目标功能：**

- 模型目录：上下文窗口、工具能力、视觉能力、区域、版本和价格。
- 路由策略：按租户、项目、任务、延迟、质量和成本选择模型。
- 失败 fallback、限流、熔断、超时、指数退避和请求取消。
- token 和成本实时统计，支持预算和预警。
- Prompt/response schema 兼容检查和供应商错误标准化。
- 离线模型、私有模型和云模型统一接入。

**企业级升级：**

- 长期凭据放入 Secret Manager，调用只获得短期访问权限。
- 对不同租户使用不同数据区域和供应商白名单。
- 记录每次模型调用的 model version、policy version、token、成本和 trace id。
- 对供应商异常执行熔断，避免故障扩散到全部 Run。

**建议模块：** 在 `src/mycode/llm/` 之上新增 `model_gateway/`、`provider_registry/`、`cost/`。

**验收结果：** 主模型不可用时，符合策略的备用模型自动接管；预算耗尽时任务进入明确的 quota exceeded 状态，而不是无限重试。

### 3.5 F05：工具中心与 MCP 能力市场

**用户价值：** 工具从“配置文件里的一组函数”升级为可发现、可审核、可版本化和可回滚的企业能力。

**目标功能：**

- 工具目录、能力描述、版本、输入输出 schema 和负责人。
- MCP server 注册、健康检查、能力发现和版本锁定。
- 工具按项目、环境、角色和 Run 动态授权。
- 工具灰度发布、禁用、回滚和兼容性检查。
- 工具调用样本、失败率、耗时、成本和使用趋势。
- 工具结果大小限制、敏感字段脱敏和不可信内容标记。

**企业级升级：**

- 工具必须声明风险等级、网络需求、数据访问范围和副作用类型。
- 高风险工具只能在 Sandbox worker 执行。
- 工具发布必须通过 schema、依赖、镜像和安全扫描。
- MCP 凭据按租户和项目隔离，支持轮换和撤销。

**建议模块：** `src/mycode/tool/` 保留执行契约；新增 `tool_registry/`、`mcp_registry/`、`sandbox/`。

**验收结果：** 未注册、已禁用、版本不兼容或超出权限的工具在执行前被拒绝，并产生结构化策略事件。

### 3.6 F06：安全执行沙箱

**用户价值：** 用户可以让 Agent 执行代码、测试和构建，而不需要把宿主机和生产凭据暴露给模型生成的命令。

**目标功能：**

- 临时工作区、只读基础镜像和可配置依赖。
- CPU、内存、磁盘、进程数、网络和时间限制。
- 网络白名单、域名解析策略和出站审计。
- 仓库凭据、云凭据和 MCP token 的短期注入。
- 构建产物、测试报告、日志和差异报告上传到 Artifact Store。
- 任务取消时可靠终止子进程并释放资源。

**企业级升级：**

- 每个执行 Attempt 都有独立 sandbox 和安全上下文。
- 使用 gVisor、Kata Containers、Firecracker 或等价隔离技术，根据风险等级分层。
- 禁止把宿主机 socket、长期 token 和未授权目录挂载到沙箱。
- 资源使用纳入租户成本和配额。

**建议模块：** `src/mycode/tool/command.py`、`filesystem.py` 改为调用 Sandbox API；新增 `sandbox/worker.py`、`sandbox/policy.py`、`artifact/`。

**验收结果：** 沙箱无法读取未授权路径、无法访问未列入白名单的网络资源；超时或取消后进程和临时文件都被清理。

### 3.7 F07：企业记忆、知识库与可审计 RAG

**用户价值：** Agent 能够长期理解项目规范、架构决策、历史故障和组织知识，同时能解释每条结论来自哪里。

**目标功能：**

- 用户记忆、项目记忆、组织知识和 Run 临时上下文分层。
- 文档、代码、Issue、PR、测试报告、构建结果的采集和增量索引。
- 关键词 + 向量 + 元数据过滤的混合检索。
- 记忆来源、更新时间、可信度、适用范围和过期时间。
- 引用片段、文件版本和原始 Artifact 链接。
- 用户纠正、删除、导出和保留期管理。

**企业级升级：**

- 原始事实存储与索引分离，向量库不能替代原始记录。
- 检索必须带租户、项目、权限和版本过滤。
- 记忆写入通过审核/质量评分，模型不能直接覆盖高可信事实。
- 记录检索 query、命中文档、模型使用的引用和最终反馈。

**建议模块：** 扩展 `src/mycode/memory/`；新增 `knowledge/ingest.py`、`knowledge/index.py`、`knowledge/retrieval.py`。

**验收结果：** 用户无权限的文档不会出现在召回结果中；回答可以展示引用来源，删除文档后索引在约定时间内失效。

### 3.8 F08：Workflow 与 Team 协同编排

**用户价值：** 用户可以把复杂目标拆成分析、实现、测试、审查、发布等阶段，由多个 Agent 或工具协同完成。

**目标功能：**

- DAG、串行、并行、条件分支、人工审批和补偿动作。
- Lead/member、Sub Agent 和普通 Tool WorkItem 统一调度。
- 任务优先级、并发限制、依赖、超时、重试和取消传播。
- 失败节点重跑、从 checkpoint 恢复和人工接管。
- Workflow 模板、版本、参数 schema 和执行报告。

**企业级升级：**

- 使用持久化 Workflow 状态，不依赖某个 supervisor 进程。
- 以 `Run -> WorkItem -> Attempt -> Event` 统一生命周期。
- 事件总线负责跨节点唤醒，数据库负责状态和版本条件更新。
- 对外部副作用使用幂等键、补偿动作和人工确认。
- 复杂流程可以接入 Temporal 等工作流引擎，但领域代码依赖自己的 Workflow port。

**建议模块：** 重构 `src/mycode/team/`、`src/mycode/subagent/`，新增 `workflow/definition.py`、`workflow/runtime.py`、`scheduler/`。

**验收结果：** 任意节点退出后，Workflow 可在其他节点继续；同一角色的消息按顺序处理，跨角色并行不产生重复副作用。

### 3.9 F09：人工协作和审批工作台

**用户价值：** 高风险操作、长时间任务和异常恢复不再只能依赖终端输入，管理员可以在 Web 或 API 中集中处理。

**目标功能：**

- 待审批列表、风险摘要、工具参数、影响范围和历史决策。
- 批准、拒绝、修改参数、转交、升级和过期。
- 任务暂停、恢复、重试、取消和人工接管。
- 团队评论、决策记录和变更原因。
- Webhook、邮件、IM 和工单系统通知。

**企业级升级：**

- 审批本身是持久化资源，有版本、幂等键和过期时间。
- 强制双人审批、职责分离和生产环境保护。
- 审批结果与策略版本、主体身份和 trace 绑定。
- 通知失败不影响审批状态，审批状态变化通过事件总线可靠投递。

**建议模块：** `approval/`、`notification/`、`api/approvals.py`，复用现有 `permission` 规则和 Agent 事件。

### 3.10 F10：可观测性、评测与持续改进

**用户价值：** 开发团队可以知道 Agent 为什么成功或失败，产品团队可以比较模型、Prompt、工具和 Workflow 版本。

**目标功能：**

- Run、模型、工具、事件和 Sandbox 的 trace。
- 延迟、成功率、重试率、死信率、token、成本和资源指标。
- Prompt/Skill/Policy/Model 的版本对比。
- 离线数据集、回放、回归评测和人工反馈。
- 失败聚类、质量评分、事实性和工具正确性检查。
- SLO、错误预算、告警和故障响应手册。

**企业级升级：**

- 所有评测样本脱敏并按租户隔离。
- 生产流量可以按比例进入 shadow/evaluation pipeline，不影响主流程。
- 任何模型或策略升级都有回归门禁和灰度开关。
- 审计日志和调试日志分离，普通日志不得包含完整 prompt、密钥或敏感工具参数。

**建议模块：** 扩展 `dev_logging.py`、`log_context.py`；新增 `observability/`、`evaluation/`、`feedback/`。

## 4. 目标企业级架构

### 4.1 分层架构

```text
客户端层
  CLI/TUI | IDE Plugin | Web Console | REST/SDK | Webhook
                              |
接入层
  API Gateway | OIDC | Rate Limit | Request Idempotency | Tenant Context
                              |
控制面
  Run API | Project API | Workflow API | Policy | Approval | Model Catalog
  Scheduler | Quota/Billing | Audit | Admin/Operations
                              |
可靠状态层
  PostgreSQL | Outbox/Inbox | Event Ledger | Redis Cache/Lease
  Object Storage | Search/Vector Index
                              |
事件与调度层
  NATS JetStream/Kafka | Consumer Groups | Retry/DLQ | Rebalance
                              |
数据面
  Agent Worker | Team Worker | Workflow Worker | Model Gateway
  Tool Sandbox Worker | MCP Connector | Context/Memory Worker
                              |
外部系统
  Model Providers | Git | CI/CD | Issue Tracker | Cloud APIs | Enterprise IM
```

### 4.2 控制面职责

控制面负责“要做什么、谁可以做、做到了哪一步、失败后怎么处理”，不直接执行用户命令。核心服务如下：

| 服务 | 职责 | 不能承担的职责 |
| --- | --- | --- |
| API Gateway | 认证、限流、路由、幂等键和请求上下文 | 不执行业务工具 |
| Run Service | 创建和查询 Run、状态迁移、事件订阅 | 不直接持有模型长连接 |
| Workflow Service | 校验流程定义、生成 WorkItem、处理依赖 | 不绕过策略执行节点 |
| Scheduler | 按租户、优先级、能力和配额分配 WorkItem | 不保存唯一业务事实 |
| Policy Service | 身份授权、风险判断、策略版本 | 不修改业务状态 |
| Approval Service | 人工审批、过期、转交和审计 | 不直接执行被审批动作 |
| Model Gateway | 模型目录、路由、限流、成本和 fallback | 不持久化完整会话历史 |
| Project Service | 项目、仓库、环境和配置管理 | 不持有模型调用状态 |

### 4.3 数据面职责

数据面 worker 是可水平扩展的执行单元：

- **Agent Worker：** 领取 Run/WorkItem，执行模型轮次、上下文构建和工具调度。
- **Team Worker：** 消费 Lead/member 事件，维护角色队列和协作协议。
- **Workflow Worker：** 执行节点依赖、条件分支和补偿动作。
- **Tool Sandbox Worker：** 在受限环境执行命令、文件、构建和测试。
- **MCP Connector：** 管理远端 MCP 生命周期、连接池、凭据和健康状态。
- **Context Worker：** 负责归档、摘要、索引和记忆更新等异步工作。

Worker 不以本地磁盘作为唯一状态，不把用户身份放在进程全局变量中，不把事件通知当作事实记录。每次执行都从共享状态领取租约，并定期写入 heartbeat。

### 4.4 状态与事件模型

```text
AgentRun
  +- WorkItem: plan / model_round / tool / approval / review / publish
       +- Attempt: worker_id / lease / heartbeat / retry_count
            +- Event: created / started / progress / result / failed / canceled
                 +- Artifact: patch / log / report / summary / output
```

状态变化要求：

1. 业务状态和 Outbox 在同一事务中提交。
2. 事件总线使用 at-least-once，消费者通过 Inbox 和版本条件实现幂等。
3. 同一 Run 或 Team role 按分区键保持顺序，不要求全局顺序。
4. 任务失败按可重试、不可重试、需人工介入三类处理。
5. 所有外部副作用必须携带 idempotency key 或定义补偿动作。

## 5. 架构演进路径

### 阶段 A：模块化单体

**目标：** 不增加分布式依赖，先把职责拆开。

- 将 Agent Loop 拆为状态机、模型端口、上下文端口、工具端口和事件端口。
- 将 Team/Sub Agent 映射到统一 WorkItem 模型。
- 将本地文件、内存实现统一为 repository adapter。
- 引入 `TenantContext`、`RunContext`、`TraceContext`，即使本地模式也带齐字段。
- 为状态迁移、错误码、事件 schema 和工具副作用补齐契约测试。

**完成标志：** 不依赖 CLI/TUI 内存状态也能重建一个 Run 的完整状态；本地 file-backed 和 memory-backed 实现通过同一套测试。

### 阶段 B：共享持久化

**目标：** 让多进程可以共享业务真相。

- PostgreSQL 保存租户、项目、Run、WorkItem、Attempt、策略和审计索引。
- 对象存储保存大 prompt、工具结果、压缩归档和构建产物。
- Outbox/Inbox 保证数据库状态和事件发布之间不丢消息。
- Redis 只用于缓存、限流和租约辅助，不承载不可恢复的业务状态。
- 提供从 `~/.mycode` 的导入、校验、双写和回滚流程。

**完成标志：** 一个进程提交任务后立即退出，另一个进程可以读取并继续执行；重复消息不会改变最终业务结果。

### 阶段 C：服务化运行时

**目标：** CLI/TUI 变成 API 客户端，Agent 运行在无状态服务中。

- 提供 Run、Event、Approval、Artifact、Project 和 Tool API。
- 通过 SSE/WebSocket 或消息订阅向客户端推送事件。
- Worker 通过队列领取 WorkItem，支持 heartbeat、优雅下线和租约接管。
- 模型调用放到 Model Gateway，工具调用放到 Tool/Sandbox Gateway。
- 通过 feature flag 逐租户切换 local runtime 和 service runtime。

**完成标志：** 客户端断线可续传；API worker 可以滚动升级；长任务不会因为连接断开而结束。

### 阶段 D：分布式数据面

**目标：** Agent、Team、工具和上下文任务可以横向扩容。

- 事件总线使用消费组和分区键路由到 Worker。
- 按模型能力、工具能力、租户配额和区域调度。
- 高风险工具进入独立 Sandbox 集群。
- Team role、Workflow node 和普通 Tool 调用共享统一的 Attempt/Lease 语义。
- 增加 dead-letter、回放、重平衡、故障注入和容量自动伸缩。

**完成标志：** 跨节点执行、故障接管、顺序保证、重复投递和最终失败都能在 E2E 测试中稳定复现和验证。

### 阶段 E：企业治理平台

**目标：** 让企业可以安全地使用、审计和控制成本。

- OIDC、组织、项目、角色、服务账号和短期凭据。
- RBAC + ABAC、审批、策略模拟、策略版本和审计。
- Model/Tool/Skill/Workflow 注册、版本、发布、灰度和回滚。
- 多租户配额、预算、成本归集、SLO 和告警。
- 数据保留、删除、导出、加密、灾备和合规报告。

**完成标志：** 企业管理员可以回答“谁在什么项目、用什么模型、调用了什么工具、产生了什么产物、花了多少成本、依据什么策略”。

## 6. API 与领域契约建议

### 6.1 Run API

建议对外暴露稳定的资源语义，而不是暴露内部 Python 类：

| 接口 | 作用 | 幂等/一致性要求 |
| --- | --- | --- |
| `POST /v1/runs` | 创建 Run | `Idempotency-Key` 必须生效 |
| `GET /v1/runs/{run_id}` | 查询状态和摘要 | 只返回当前租户可见数据 |
| `GET /v1/runs/{run_id}/events` | 按 cursor 读取事件 | 已确认事件可重复读取但不重复执行 |
| `POST /v1/runs/{run_id}/cancel` | 取消 Run | 重复调用返回相同终态 |
| `POST /v1/runs/{run_id}/pause` | 暂停 | 只在安全检查点暂停 |
| `POST /v1/runs/{run_id}/resume` | 恢复 | 检查权限、版本和配额 |
| `POST /v1/runs/{run_id}/retry` | 重试失败节点 | 指定 WorkItem，不能隐式重跑全部副作用 |
| `GET /v1/runs/{run_id}/artifacts` | 读取产物清单 | 访问 Artifact 时再次校验权限 |

### 6.2 内部事件

事件至少包含：

```text
event_id
event_type
schema_version
tenant_id
project_id
run_id
work_item_id
attempt_id
producer
occurred_at
trace_id
idempotency_key
payload_ref
```

大字段使用对象存储引用，事件本体保存摘要、hash、大小和内容类型。事件 schema 采用向后兼容策略，新消费者可以忽略可选字段，删除字段必须经过迁移窗口。

### 6.3 Tool 契约

每个工具必须声明：

- `tool_name`、`version` 和能力标签。
- 输入 schema、输出 schema 和最大结果大小。
- 风险等级、所需权限、网络需求和可访问资源。
- 是否有外部副作用、幂等方式和补偿方式。
- 超时、重试、取消和部分结果语义。
- 负责人、健康检查、发布状态和兼容范围。

## 7. 企业级功能优先级

| 优先级 | 功能 | 原因 | 前置依赖 |
| --- | --- | --- | --- |
| P0 | Run Center、统一状态机、幂等、checkpoint | 没有它就无法可靠恢复和服务化 | Agent Loop、Team、Session |
| P0 | 存储/事件端口、PostgreSQL、Outbox/Inbox | 分布式共享真相的基础 | TeamStore、EventStore |
| P0 | 身份上下文、权限边界、审计字段 | 企业数据隔离和责任追踪的基础 | API、Policy |
| P0 | Sandbox 和工具副作用治理 | 防止 Agent 直接危害宿主环境 | Tool、MCP、Worktree |
| P1 | Run API、事件流、审批 API | 支持 CLI/TUI 之外的客户端 | Run、Event、Identity |
| P1 | Model Gateway、成本、fallback | 供应商治理和可用性 | Provider adapters、Usage |
| P1 | Workflow/Team 分布式调度 | 支持复杂任务和横向扩展 | Event Bus、Scheduler |

## 9. 数据、一致性和故障策略

### 9.1 任务创建

1. API 校验身份、项目权限、配额和幂等键。
2. 事务写入 Run、初始 WorkItem、审计记录和 Outbox。
3. 提交事务后发布 `run.created`。
4. Scheduler 根据能力和配额投递 `work_item.ready`。
5. Worker 领取 Attempt 并写入 lease/heartbeat。

### 9.2 Worker 故障

- heartbeat 超时后，租约进入可接管状态。
- 新 Worker 领取前必须检查状态版本。
- 已提交结果的 WorkItem 不再执行；只发布缺失的后继事件。
- 无法判断外部副作用是否已经发生时，进入人工确认或补偿队列，不能盲目重跑。

### 9.3 事件故障

- 数据库提交成功、发布失败：Outbox 重试。
- 发布成功、消费者 ACK 丢失：Inbox 幂等处理。
- 消费持续失败：指数退避，超过上限进入 DLQ。
- 事件 schema 不兼容：拒绝消费并告警，不静默丢弃。
- 事件总线不可用：Run 状态保留为可恢复状态，API 返回明确的暂时不可用。

### 9.4 模型与工具故障

- 模型超时、限流和临时网络错误可重试。
- 参数错误、权限拒绝、目标不存在不可重试。
- 工具副作用必须使用幂等键或补偿事务。
- 结果过大先归档，再把引用和摘要交给模型。
- 工具返回的外部文本默认是不可信上下文，不能覆盖系统策略。

## 10. 版本、发布和兼容策略

- Model、Tool、Skill、Hook、Workflow 和 Policy 都使用显式版本。
- Run 固定引用创建时的版本集合，后续升级不改变正在运行的任务语义。
- 新事件只新增可选字段；删除字段至少经过一个兼容窗口。
- API 使用 `/v1`、`/v2` 版本路径，内部事件使用 `schema_version`。
- 所有新功能通过 feature flag 按本地、开发租户、灰度租户逐步打开。
- 发布前必须完成单元、契约、集成、E2E、迁移、回滚和安全测试。
- Skill/MCP/Tool 包发布前检查依赖、权限、镜像签名和许可证。

## 11. 测试与验收矩阵

| 领域 | 必须验证的场景 | 通过标准 |
| --- | --- | --- |
| Run | 重复创建、断线重连、暂停、恢复、取消 | 状态幂等、事件可续传 |
| Workflow | 并行、依赖、失败重跑、补偿 | 不重复执行外部副作用 |
| Team | Lead/member 跨节点通信、顺序和重试 | 节点故障后可接管 |
| Storage | DB 提交、迁移、导入、回滚 | 数据校验一致，可恢复 |
| Event | Outbox、Inbox、重复、乱序、DLQ | 不丢事实，不重复产生结果 |
| Policy | 跨租户、权限撤销、审批过期 | 默认拒绝，审计完整 |
| Tool | 沙箱逃逸、超时、网络限制、凭据 | 未授权资源不可访问 |
| Model | fallback、熔断、限流、预算 | 失败可解释，不无限重试 |
| Memory | 权限过滤、删除、索引延迟、引用 | 不越权召回，来源可追溯 |
| Operations | 滚动升级、节点宕机、灾备恢复 | 在目标 SLO 内恢复 |

## 12. 分阶段开发计划

### M1：领域模型和端口冻结

- 定义 Run、WorkItem、Attempt、Event、Artifact、Approval 和 PolicyDecision。
- 明确每个状态的合法迁移、终态和错误码。
- 为 file-backed、memory-backed 实现建立 contract tests。
- 给现有 Agent Loop、Team、Sub Agent 接入统一上下文和幂等键。

### M2：持久化与可靠事件

- 建立 PostgreSQL schema 和 migration。
- 实现 repository、outbox、inbox、lease、heartbeat 和 DLQ。
- 提供 `~/.mycode` 导入工具和双读校验。
- 先迁移 Team，再迁移 Session、Memory 和 Run。

### M3：Run API 与服务化 Worker

- 实现 Run/Events/Approval/Artifact API。
- 将 CLI/TUI 改成 API client，同时保留 local mode。
- 将模型调用、工具调用和上下文处理做成可恢复 WorkItem。
- 增加跨进程和跨节点 E2E。

### M4：安全工具和企业治理

- 接入 OIDC、租户、项目和 RBAC/ABAC。
- 建立 Tool/MCP Registry 和 Sandbox Worker。
- 接入 Secret Manager、审计、脱敏和数据保留。
- 通过权限撤销、跨租户、沙箱逃逸和秘密扫描测试。

### M5：模型、Workflow 和知识平台

- 建立 Model Gateway、成本计量、fallback 和评测回放。
- 将 Team/Sub Agent 升级为统一 Workflow。
- 建立知识采集、混合检索、引用和反馈机制。
- 逐步加入模板、插件和组织知识治理。

### M6：高可用和规模化运营

- Kubernetes 多副本、自动伸缩、多可用区和灾备。
- OTel、SLO、容量模型、混沌测试和错误预算。
- 灰度、回滚、跨区域、计费和租户级成本治理。

## 13. 企业级完成标准

未来功能改造达到企业级基础版本，至少需要满足：

- 任务有统一 Run API、状态机、事件 cursor、checkpoint、暂停、恢复、取消和重试能力。
- Agent、Sub Agent、Team 和 Workflow 使用统一 WorkItem/Attempt 生命周期。
- PostgreSQL/对象存储保存业务真相，事件总线负责可靠分发，outbox/inbox 和幂等测试通过。
- CLI、TUI、IDE 和 Web 使用相同的 API/Event 契约，客户端断线不会丢失任务。
- 组织、租户、项目、身份、角色、策略、审批、配额和审计闭环完成。
- Model、Tool、MCP、Skill、Hook 和 Workflow 都有注册、版本、权限、灰度和回滚机制。
- 高风险工具运行在隔离 Sandbox，具备资源、网络、凭据和副作用治理。
- 记忆和知识检索有租户权限过滤、引用、删除、保留期和原始事实恢复能力。
- 所有关键链路具备 trace、指标、日志、成本、SLO、告警和故障响应手册。
- 经过节点故障、消息重复、网络分区、供应商故障、迁移回滚、负载和安全测试。

## 14. 不建议提前做的功能

- 没有可靠 Run 状态机之前，不要继续扩展更多 Team 角色和复杂调度。
- 没有 Sandbox 之前，不要默认开放任意宿主机命令和网络访问。
- 没有租户隔离之前，不要实现组织级共享记忆和跨项目知识库。
- 没有 Model Gateway 之前，不要在业务代码中散落供应商 fallback 和成本逻辑。
- 没有事件版本和迁移策略之前，不要让 Skill、Tool、Workflow 直接修改核心事件格式。
- 没有评测和回滚之前，不要把 Prompt、模型或策略升级直接推到全部租户。
- 不要把向量数据库当作知识系统唯一真相，也不要把消息队列当作业务状态库。

## 15. 最终建议

下一步按以下顺序推进：

1. 先完成 Run/WorkItem/Attempt/Event 领域模型和端口抽象。
2. 再完成 PostgreSQL、Outbox/Inbox、租约和 checkpoint，让任务可恢复。
3. 然后提供 Run API，把 CLI/TUI 变成客户端，把 Agent 变成无状态 Worker。
4. 在服务化基础上接入身份、租户、策略、审计和 Sandbox。
5. 最后扩展 Model Gateway、Workflow、知识库、评测、弹性和商业化能力。

这条路线的核心是把“Agent 会做什么”与“平台如何可靠地运行 Agent”分开。功能层可以持续增加模型、工具和 Workflow，但所有新功能都必须接入统一的 Run、Policy、Event、Artifact 和 Observability 契约，才能在保持本地开发效率的同时，逐步升级为可治理、可恢复、可扩展的企业级分布式 Agent 平台。
