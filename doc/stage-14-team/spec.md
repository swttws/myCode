# myCode Stage 14：长期团队协作规格说明

## 背景

myCode 已支持定义式与 Fork 式子 Agent、会话内后台任务、显式 Worktree 隔离、权限策略、工具注册和上下文压缩，但这些能力仍以一次会话和一次任务为边界。子 Agent 不能跨进程恢复，不能共享任务板或邮箱，也没有 Lead 负责把一个用户目标拆成依赖任务并在本地统一合并成果。

本阶段把主 Agent 升级为 Team Lead，并引入长期存在的小组。小组状态、成员上下文、共享任务和邮箱持久化到用户目录；成员可以使用独立终端窗格或同进程协程运行；Lead 可以在普通模式亲自编码，也可以在双重开关开启后进入 coordinator 模式，把代码修改交给成员。

## 目标

- 提供绑定单个 Git 仓库的长期小组对象，支持创建、接管、归档和跨进程恢复。
- 记录成员角色、角色版本、稳定工作目录、本地分支、运行后端、审批要求、邮箱和可恢复上下文。
- 支持 `tmux`、Windows Terminal 和同进程协程三类成员后端，并提供可观测、不可静默的自动选择。
- 向团队成员提供共享任务板和点对点/广播邮箱；普通主 Agent、普通子 Agent 不暴露这些协作工具。
- 支持简单有向无环任务依赖、原子领取、任务批次、计划审批和成员空闲/阻塞通知。
- 让 Lead 自主拆解用户目标、派生成员、管理任务、处理审批，并在批次完成后执行本地原子 Git 合并。
- 让成员自然停止后保持 idle，Lead 通过消息唤醒并从磁盘恢复成员上下文继续工作。
- 提供 coordinator 双锁模式，移除 Lead 的文件写工具并限制 shell，只保留编排和受控本地 Git 集成能力。
- 在所有流程中硬性禁止 `git push` 和其他远端写操作。

## 功能需求

### F1：长期小组与仓库绑定

系统提供长期小组对象。小组必须绑定一个本地 Git 仓库和一个固定的本地目标分支；默认目标分支为创建小组时的当前分支，也可由全局配置指定。小组名称必须可安全作为跨平台目录名使用。

小组持久化在用户目录按小组名划分的目录中。小组可处于活动、归档或异常待处理状态。一个 Lead 会话同一时间只能激活一个小组。

### F2：Lead 租约与接管

活动小组只能存在一个有效 Lead 租约。第二个进程在租约有效时不能接管；租约被明确释放或经有界检查确认已过期后，新的 Lead 会话才能接管。

主会话执行 `/clear` 或退出时释放租约，但不删除小组、成员、任务、邮箱或上下文。新的会话可以按名称接管小组。多个持久化小组可以同时存在，但一个 Lead 会话只允许一个活动小组。

### F3：成员花名册与角色快照

每名成员至少记录唯一名称、角色名、角色版本指纹、稳定 worktree、稳定本地分支、请求后端、实际后端、是否需要 Lead 审批、运行状态、邮箱位置、上下文位置和最近活动时间。

成员角色复用现有角色目录和优先级规则。创建成员时固定角色版本；恢复时角色版本不匹配必须暂停恢复并报告，不得静默加载新角色。成员不能递归创建团队成员。

小组默认最多登记 16 名成员、同时运行 4 名成员；空闲成员不占运行名额。两个上限可由全局配置在系统硬上限内调整。

### F4：成员运行后端

成员支持以下请求后端：

- `auto`：按 `tmux`、Windows Terminal 原生窗格、同进程协程的顺序选择；
- `tmux`：使用独立终端窗格运行完整成员实例；
- `terminal`：使用当前平台可用的原生终端分屏能力；Stage 14 至少支持 Windows Terminal；
- `in_process`：使用同进程异步协程运行独立 AgentLoop。

自动选择必须记录实际后端和选择原因。显式指定的后端不可用时直接失败，不静默降级。能力探测失败、窗格创建失败或宿主无法建立唤醒端点时，成员不得进入运行状态。

### F5：成员工作区与上下文

每名成员在小组生命周期内拥有稳定的独立 worktree 和本地分支；不得与其他成员共享工作目录。worktree 生命周期复用现有安全路径和 Git 保护规则，但小组成员目录不会在单个任务完成后自动删除。

成员运行时使用独立消息历史、权限会话、文件缓存、用量、取消信号和错误状态；共享模型访问基础设施、Hook、工具实现和路径安全规则。上下文在安全点按现有压缩机制规范化并原子落盘，受全局大小上限约束。

成员自然完成或暂时没有任务时进入 `idle`，保存上下文并通知 Lead。Lead 发送新消息后，系统从磁盘恢复同一成员上下文继续指派。外部窗格宿主保持等待并接受唤醒；宿主异常退出时在原窗格或替代窗格恢复。协程成员在进程退出后保存检查点，下次消息到达时恢复。

### F6：团队工具可见性与权限

普通主 Agent 只看到稳定的团队管理入口，用于创建或接管小组和读取当前小组状态。小组激活成功后的下一安全点，Lead 才获得 Lead 工具集。

Lead 工具集包含成员派生、优雅终止、任务增删查改、状态查询、消息、审批和本地批次合并。普通 Team Lead 保留现有普通工具和 `Agent` 工具。

团队成员工具集包含共享任务增删查改、任务领取、消息、广播、计划提交和状态通知。普通子 Agent 永远看不到团队工具，团队成员不能执行普通 `Agent` 递归委派。

工具可见性和执行权限均由权限层强制执行；仅从提示词中隐藏工具不视为安全控制。

### F7：工作批次与任务板

每个用户目标建立一个持久化工作批次。批次记录目标说明、目标分支基线、任务集合、集成状态和最终诊断；批次完成后小组可以继续接收新批次。

任务至少包含标题、行为描述、依赖任务 ID、交付类型、负责人、状态、计划版本、审批状态、提交 ID、验证摘要和错误信息。交付类型为代码交付或只读交付。

任务支持 `pending / claimed / awaiting_approval / running / blocked / completed / failed / cancelled` 状态。依赖必须形成简单 DAG；引用不存在的任务、自依赖和循环依赖立即拒绝。只有全部前置任务完成后任务才可领取。

任务领取使用版本检查原子完成，同一时刻只能有一个负责人。Lead 可分配、改派、取消和修改批次级状态；成员可以创建任务、读取任务、领取可执行任务和更新自己负责的任务。未开始且没有后继依赖的任务可以被删除，终态任务保留历史记录。

成员异常退出且无法自动恢复时，所属任务进入 `blocked`，保留成员上下文、分支和 worktree；Lead 必须明确选择恢复、改派或取消，不自动重复执行。

### F8：邮箱与名称注册表

小组目录维护名称注册表，将成员名称映射到邮箱文件、上下文位置、工作目录、运行后端和唤醒端点。邮箱按成员分文件持久化。

一条消息至少包含稳定消息 ID、协议类型、发件人、目标或广播标记、正文、摘要、时间戳和已读状态。落盘时系统自动补齐时间戳，默认未读。正文和摘要受有界大小限制。

邮箱文件使用锁文件保护并发追加和读取。拿不到锁时按配置重试；锁超过过期阈值视为失效并可回收。写入采用原子方式，禁止产生半条消息。

### F9：消息投递与结构化协议

点对点消息先通过名称注册表定位目标，再追加到目标邮箱；广播为向除发件人外的所有当前成员分别投递。发送成功只表示消息已可靠落盘，不表示目标已经处理。

系统支持以下结构化协议：

- `message`：普通点对点消息；
- `broadcast`：广播消息；
- `plan_submit`：成员提交任务 ID、计划版本和执行计划；
- `plan_decision`：Lead 对指定任务版本批准或驳回，并附原因；
- `status_update`：成员报告 idle、completed、blocked 等状态；
- `shutdown_request` 与 `shutdown_response`：优雅终止握手。

同进程成员通过运行时事件唤醒；独立进程成员在邮箱落盘后额外触发目标窗格宿主唤醒。接收方按顺序消费未读消息，消息成功注入上下文且检查点持久化后才标记已读；崩溃可导致重投，但稳定消息 ID 必须去重。

### F10：计划审批

需要审批的成员在开始任务前可以读取必要的工作区信息并形成计划，但不得执行代码修改、提交或 shell 写操作。成员通过 `plan_submit` 提交任务 ID、计划版本、计划内容和预期交付。

Lead 必须通过 `plan_decision` 明确批准或驳回同一任务版本。只有匹配版本的批准决定才能使任务进入 `running`；驳回必须包含原因，成员修改计划后递增版本并重新提交。Lead 租约不可用时，计划保持待审批。

### F11：Lead 编排

Lead 接收用户目标后创建工作批次，拆解出带依赖的任务，选择成员并写入共享任务板，然后派生成员或让空闲成员领取可执行任务。Lead 自主处理成员计划审批、状态跟踪、消息协调和批次收尾。

除不可恢复失败、无法解决的冲突、权限阻塞、仓库状态异常或租约冲突外，流程不要求用户逐项确认。成员完成代码任务时必须本地提交且不得 push；只读任务必须提供结构化结果和验证摘要。

### F12：本地原子合并

批次合并前，Lead 目标工作区必须干净、目标分支身份必须匹配批次记录，且没有 Lead 未提交修改。系统在临时本地集成分支中按依赖拓扑顺序、再按稳定顺序合并成员成果。

冲突转成代码任务，派给成员在临时集成工作区解决、验证并提交；Lead 不直接修改冲突文件。成员无法解决时终止临时集成，目标分支保持原样，相关分支、worktree 和上下文保留并上报。

所有合并和验证成功后才更新目标分支。只对空闲、干净且成果已集成的成员分支同步新基线。系统不自动 stash、提交、覆盖或复制 Lead 的未提交内容。

### F13：coordinator 双锁模式

coordinator 必须同时满足：

1. 全局配置中的能力开关已开启；
2. 用户环境变量主动启用；
3. 当前会话已经激活一个小组。

三项在会话启动/接管时确定，运行中不动态切换。未启用时，普通 Team Lead 保留现有工具并可亲自编码。

启用后，Lead 的文件写工具和普通 `Agent` 被移除；Lead 保留只读工具、任务和成员编排、任务审批、消息、状态查询、本地原子合并以及受限 shell。受限 shell 只允许只读命令和明确的本地 Git 集成命令，禁止通过 shell 绕过文件写入限制。

### F14：终止与归档

Lead 终止成员时先发送 `shutdown_request`，成员保存上下文并确认空闲后返回 `shutdown_response`；超时后才强制结束进程或协程。任务、邮箱、上下文、分支和 worktree 保留。

Lead 可以显式归档小组。归档前必须优雅终止成员并确认没有运行任务或未处理成果；归档后目录和历史邮箱保留为只读，不再接受新任务、消息或成员派生。

### F15：不可关闭的远端写入禁令

所有成员、Lead、普通子 Agent、协作工具、窗格后端和 shell 都禁止 `git push` 及其他远端写操作。该禁令由命令权限层和 Git 集成层共同执行，不提供配置或提示词绕过入口。

## 非功能需求

- **N1：领域边界。** 小组、任务板、邮箱、成员恢复、后端选择和 Lead 编排集中在独立 Team 领域；AgentLoop、Worktree、Permission、Tool Registry、Session 和上下文压缩只通过明确接入点复用。
- **N2：状态隔离。** 任意成员的消息、权限授权、缓存、用量、取消和错误状态不得影响其他成员、Lead 或普通子 Agent。
- **N3：持久化一致性。** 小组元数据、任务状态、邮箱追加、已读标记、角色快照和上下文检查点必须在锁保护下原子更新；崩溃恢复不得产生半状态。
- **N4：并发确定性。** 同一租约、任务、邮箱、成员端点或批次合并的并发操作必须串行化；单个任务最多一个负责人、一个终态和一次完成通知。
- **N5：权限单调性。** coordinator、角色、后台后端和 shell 限制只能保持或收紧有效权限；不得通过隐藏 schema、窗格输入或命令拼接绕过权限。
- **N6：安全失败。** 路径、仓库、角色版本、锁、邮箱、后端端点或 Git 状态无法确认时拒绝继续，并保留现场。
- **N7：资源有界。** 默认最多登记 16 名成员、同时运行 4 名成员；任务、消息、摘要、上下文、锁重试和诊断均有全局配置的有限上限，超限产生稳定错误。
- **N8：跨平台。** Windows、Linux 和 macOS 保持相同团队语义；能力探测决定可用窗格后端，协程后端提供普适运行路径，显式不可用后端不降级。
- **N9：无远端副作用。** 流程不得 push、创建远端分支、修改远端配置或调用远端写入接口；本地 Git 合并是唯一允许的代码集成副作用。
- **N10：可观测性。** 小组、成员、批次、任务、消息和合并操作都有稳定 ID、状态、时间和有界诊断；后端选择、唤醒、恢复、审批和保护原因可查询。
- **N11：隐私。** 日志和错误不得包含凭据、环境变量值、完整对话、完整邮箱正文或无界 Git 输出；用户目录持久化文件只保存恢复所需内容。
- **N12：中文规范。** 系统生成的 Lead/成员提示、协议错误、状态和诊断使用中文；角色正文保持原文；新增定义类字段和复杂状态转换添加简洁中文注释。
- **N13：兼容性。** 未激活小组时现有聊天、Agent、权限、Hook、Skill、MCP、Memory、Session、Slash、TUI 和 Worktree 行为保持兼容。
- **N14：测试隔离。** 测试使用临时用户目录、临时 Git 仓库、fake LLM、fake mailbox、fake locks 和 fake pane adapters，不访问真实远端、真实用户状态或工作区外路径。

## 不做的事

- 不做跨机器或分布式团队，不做远端消息传输。
- 不做成员间实时流式输出、共享实时编辑或文件同步。
- 不做条件依赖、优先级调度、依赖回退、投票或复杂依赖约束；只做简单 DAG。
- 不允许普通子 Agent 或团队成员递归创建更多团队成员。
- 不支持一个小组绑定多个 Git 仓库，不支持目标分支在活动批次中切换。
- 不自动 stash、提交、覆盖或复制 Lead 的未提交修改。
- 不自动 push、pull、fetch 后再修改远端状态，不创建远端分支。
- 不提供绕过保护的强制删除 worktree 或强制删除归档历史入口。
- 不提供图形化团队面板、远程市场或插件角色发现。
- 不把 `/clear` 解释为解散长期小组，也不跨小组共享任务或邮箱。

## 验收标准

- **AC1（F1-F2）**：创建小组后，用户目录出现按名称隔离的持久化目录；小组绑定仓库身份和目标分支；有效 Lead 租约阻止第二进程接管，过期租约可安全接管。
- **AC2（F3）**：成员记录角色、角色版本、稳定 worktree、分支、请求/实际后端、审批要求、邮箱、上下文和状态；角色文件变化不会被静默使用。
- **AC3（F4）**：`auto` 按 `tmux → terminal → in_process` 选择并报告原因；显式不可用后端直接失败；窗格创建失败不会留下运行中的成员。
- **AC4（F5）**：两个成员使用不同消息、权限、缓存、用量和工作区状态；一个成员的状态变化不改变 Lead 或其他成员。
- **AC5（F5）**：成员自然完成后进入 `idle` 并通知 Lead；Lead 发送消息后，成员从磁盘检查点恢复并继续原上下文。
- **AC6（F6）**：普通入口只看到稳定团队管理入口；激活小组后的下一安全点 Lead 获得 Lead 工具；普通子 Agent 看不到团队工具；成员不能递归派生。
- **AC7（F7）**：每个用户目标形成独立批次；任务支持增删查改、负责人和状态；任务依赖拒绝悬空、自依赖和循环，前置任务未完成时不能领取。
- **AC8（F7）**：并发领取同一任务只能成功一次；成员可原子领取未分配的可执行任务；Lead 可分配、改派、取消和修改批次状态。
- **AC9（F7）**：代码任务未提交或验证摘要缺失时不能完成；只读任务可用结构化结果和验证摘要完成。
- **AC10（F8-F9）**：点对点、广播和全部结构化协议消息正确落盘；消息自动获得时间戳且默认未读；邮箱锁竞争按配置重试，过期锁可回收。
- **AC11（F9）**：消息成功注入上下文并完成检查点后才标记已读；模拟崩溃会重投但稳定消息 ID 不会重复应用。
- **AC12（F10）**：需要审批的成员可读取必要信息并提交计划，但批准前不能修改文件、提交或执行 shell 写操作；只有匹配任务 ID 和计划版本的批准决定能启动任务。
- **AC13（F11）**：Lead 能从用户目标创建批次、拆分依赖任务、派生成员、处理审批并跟踪状态；正常流程不要求用户逐项确认。
- **AC14（F12）**：Lead 目标工作区有未提交修改时合并直接拒绝，不 stash、不覆盖；干净时在临时本地集成分支完成合并。
- **AC15（F12）**：可解决冲突被转成成员任务；成员提交后可继续集成；无法解决时目标分支保持原样，所有成员成果和诊断保留。
- **AC16（F13）**：配置开关、环境变量和活动小组缺一不可；coordinator 隐藏文件写工具和普通 `Agent`，保留任务/成员编排、消息、审批、查询、读工具和受限 shell。
- **AC17（F13、F15）**：coordinator 或任意成员通过文件工具、窗格输入或 shell 尝试 push/远端写操作均被拒绝并产生稳定诊断。
- **AC18（F14）**：终止成员先完成优雅握手；超时才强制结束；任务、邮箱、上下文、分支和 worktree 均保留。
- **AC19（F14）**：归档前必须没有运行任务或未处理成果；归档后小组目录可读但不能继续派生、写任务或投递消息。
- **AC20（F2、F5）**：`/clear`、Lead 进程退出和应用重启不会删除小组；外部成员可继续运行，协程成员可从检查点恢复，新的 Lead 可在租约过期后接管。
- **AC21（N4）**：同一任务、邮箱、租约和批次合并的并发竞争不会产生重复负责人、重复终态、重复通知或双重删除。
- **AC22（N7）**：达到成员、任务、消息、上下文、锁重试或诊断上限时操作失败并返回有界稳定错误，不无限增长磁盘或内存。
- **AC23（N8）**：Windows、Linux 和 macOS 的能力探测结果不同，但任务、消息、审批、恢复和合并语义一致；显式后端不可用时不降级。
- **AC24（N10-N12）**：小组、成员、批次、任务、消息、后端、唤醒、审批和合并状态均可查询；日志不含凭据、环境变量、完整对话或无界 Git 输出，新增定义字段有中文注释。
- **AC25（N13-N14）**：未激活小组时现有 Agent、Session、Slash、TUI、Permission、Hook、Skill、MCP、Memory 和 Worktree 回归测试全部通过；团队测试只使用临时资源和 fake 依赖。
- **AC26（端到端）**：Lead 创建批次并派生两个成员，成员分别完成有依赖的代码任务并提交本地分支；一个成员 idle 后被消息唤醒恢复上下文，批次最终在本地原子合并，目标分支更新且未发生 push。
- **AC27（端到端失败）**：目标工作区脏、角色版本变化、成员恢复失败、邮箱锁长期占用或冲突无法解决时，系统失败关闭并保留现场，不覆盖用户内容。
