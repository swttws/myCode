# Stage 15 Team 工具拆分 Spec

## 背景

当前 team coordinator 通过 `TeamTool` 的多个视图承载团队生命周期、批次、成员、任务、计划、消息、关停和本地整合等能力。每个视图仍然使用 `action` 字段和大型 `oneOf` 参数 schema 进行二次路由。模型需要同时判断工具视图、动作名称、角色限制和动作专属参数，容易产生工具误选、参数串用和无效调用。

本阶段只改造模型可见的工具边界和相关注册、权限、文档、测试引用。底层团队服务、持久化、邮箱、工作树、后端和协议语义继续复用现有实现。

## 目标

- 将 team 能力拆成一个工具对应一个明确意图的原子工具集合。
- 移除所有模型可见的 `action`/`operation` 二次路由字段。
- 用 `team_<资源>_<动作>` 的稳定小写下划线命名工具。
- 根据主会话、团队 Lead、团队 Member 角色精确裁剪工具可见性，并在执行前拒绝隐藏工具。
- 按选择 B 一次性移除旧工具名 `team`、`team_lead`、`team_member`，不提供别名或双注册。
- 保持现有团队状态机、持久化格式、邮箱协议、权限审批和 Agent Loop 行为不变。
- 统一工具描述、参数说明、模型提示、权限展示和错误说明为中文。

## 功能需求

### F1：原子工具目录

系统必须注册以下 21 个新工具；每个工具只负责一个意图，不接受 `action` 或 `operation` 字段：

| 领域 | 工具 |
|---|---|
| 团队 | `team_create`、`team_attach`、`team_status`、`team_archive` |
| 批次 | `team_batch_start`、`team_batch_integrate` |
| 成员 | `team_member_spawn`、`team_member_terminate` |
| 任务 | `team_task_create`、`team_task_list`、`team_task_get`、`team_task_update`、`team_task_delete`、`team_task_claim`、`team_task_transition` |
| 计划 | `team_plan_submit`、`team_plan_decide` |
| 消息与生命周期 | `team_message_send`、`team_status_update`、`team_shutdown_request`、`team_shutdown_response` |

### F2：团队生命周期

- `team_create` 只能创建新团队；目标团队已存在时返回结构化失败。
- `team_attach` 只能接管已有团队；目标团队不存在或不满足现有接管约束时返回结构化失败。
- `team_status` 返回当前团队、成员和批次摘要。
- `team_archive` 只能归档满足现有服务约束的安静团队，并返回归档后的状态。
- 创建、接管、归档的租约和状态校验保持现有语义。

### F3：批次与成员编排

- `team_batch_start` 创建团队批次并返回批次标识、目标和状态。
- `team_member_spawn` 启动成员，明确绑定角色、角色版本、任务、批次、后端、工作树和审批策略。
- `team_member_terminate` 支持正常停止和显式强制停止，并返回成员最终状态。
- `team_batch_integrate` 按现有依赖顺序整合完成任务的本地提交，并返回整合状态、结果提交或冲突任务。

### F4：任务生命周期

任务的创建、列表、读取、更新、删除、领取和状态转换分别由独立工具完成：

- 所有并发写操作继续要求 `expected_revision`。
- Member 工具自动使用绑定成员身份，不能通过参数伪造其他成员。
- 任务所有者校验、阻塞恢复限制、成员审批前运行限制和结果字段保留现有行为。
- 任务列表和读取不得修改持久化状态。

### F5：计划、消息和关停协议

- `team_plan_submit` 提交任务计划，更新计划版本并进入等待审批状态。
- `team_plan_decide` 校验计划版本后批准或拒绝；拒绝时必须提供原因。
- `team_message_send` 支持定向消息和广播消息，保留任务和批次元数据。
- `team_status_update` 发送成员状态更新。
- `team_shutdown_request` 和 `team_shutdown_response` 保留现有 checkpoint-before-ack 语义。

### F6：角色可见性

工具列表按运行角色裁剪，隐藏工具不能通过直接调用绕过：

| 运行角色 | 可见工具范围 |
|---|---|
| 未激活的主会话 | `team_create`、`team_attach`、`team_status` |
| 已激活的 Lead | `team_status`、`team_archive`、批次工具、成员编排工具、任务工具、`team_plan_decide`、`team_message_send`、`team_shutdown_request` |
| Member 运行时 | 任务工具、`team_plan_submit`、`team_message_send`、`team_status_update`、`team_shutdown_response` |

Lead 不得看到 Member 专属的计划提交、状态更新和关停响应；Member 不得看到团队创建、接管、成员编排、批次整合和归档工具。

### F7：独立参数契约

- 每个工具拥有独立 JSON Schema，顶层为单一对象。
- Schema 只声明自身需要的字段，明确必填字段、枚举、默认行为，并设置 `additionalProperties: false`。
- 工具描述、参数描述、模型提示、权限拒绝展示和用户可见错误说明使用中文。
- 参数错误必须在调用服务前返回结构化失败，不产生副作用。

### F8：工具分类与权限

- 团队状态、任务列表、任务读取声明为读工具。
- 创建、更新、删除、状态变更、消息、成员控制、批次控制、计划审批和归档声明为写工具。
- Lead 编排工具沿用现有团队权限特例。
- Member 的工作区写入仍受成员审批策略和全局权限系统共同约束。

### F9：一次性迁移

- 旧工具名 `team`、`team_lead`、`team_member` 不再注册，不出现在模型工具列表或角色可见性集合中。
- CLI、Worker、权限策略、Hook、Skill 工具白名单、配置示例、README 和测试统一迁移到新名称。
- 配置或扩展仍引用旧名称时，启动或加载阶段必须给出中文错误并拒绝继续使用该引用，不静默兼容。

### F10：可观测性与测试覆盖

- 工具调用事件、权限决定、日志和结构化结果携带新的完整工具名。
- 每个新工具至少覆盖 schema、成功路径、缺参、多参、角色隐藏和权限拒绝测试。
- 任务类工具额外覆盖成员身份绑定、任务所有者和版本冲突。
- 至少有一个端到端场景覆盖 Lead 创建任务、Member 领取并完成、Lead 整合批次。

## 非功能需求

### N1：行为与数据兼容

拆分只改变模型可见工具契约和注册方式，不改变团队目录结构、JSON/JSONL 持久化格式、邮箱协议、任务状态机、工作树命名、后端启动参数和本地整合规则。

### N2：Schema 简洁性

每个工具不得包含 `action`、`operation` 等二次路由字段，不使用跨动作的大型 `oneOf`。只有业务字段需要离散约束时才使用 `enum`。

### N3：安全边界不降级

工具可见性过滤、角色权限、成员身份绑定、任务所有者校验、计划版本校验、工作区范围检查、全局权限审批和协调器限制必须继续生效。隐藏工具的直接调用必须在执行前被拒绝。

### N4：无额外模型成本

拆分不得新增模型调用、后台 watcher 或跨进程服务；不改变 Agent Loop 的轮次、上下文压缩和取消语义。

### N5：命名与代码规范

对外工具名使用 `team_<资源>_<动作>` 的英文小写下划线；Python 文件、函数和变量使用 `snake_case`，类使用 `PascalCase`，常量使用全大写下划线。复杂校验、角色绑定和协议转换处添加简洁中文注释，普通直线代码不添加无效注释。

### N6：中文提示一致性

工具名称之外的模型可见文本统一使用中文。`reason_code`、枚举值和协议字段保持现有英文稳定值，供程序和 Hook 匹配。

### N7：可诊断性

工具事件、权限决定和结构化结果必须携带新的完整工具名。参数校验失败至少包含工具名、英文 `reason_code`、失败字段和中文说明；不把业务异常堆栈直接暴露给模型。

### N8：验证门槛

所有受影响的单元、集成、端到端和文档测试必须迁移并通过；自动化检查必须证明旧工具名不再注册、旧 `action` 字段不再出现在新工具 schema 中。

## 不做的事

- 不重写 `TeamService`、`TeamStore`、`TaskBoard`、`MailboxStore`、Worktree 或 Backend 的核心业务实现。
- 不修改团队持久化目录、JSON/JSONL 字段、邮箱协议、checkpoint 语义、任务状态枚举或本地 Git 整合规则。
- 不新增动态工具发现、工具搜索、远程工具注册或运行时生成 schema 的机制。
- 不保留旧工具名的别名、转发器或双注册；历史名称只允许出现在迁移错误提示中。
- 不改变 Agent Loop 的消息协议、事件类型、上下文压缩、取消、超时和批量执行规则。
- 不重新设计普通文件、命令、MCP、Skill 或 `Agent` 工具，只更新其白名单和可见性引用。
- 不改变团队角色模型、成员后端选择策略、权限档位和审批策略。
- 不引入图形化团队管理界面、远程团队协作、跨机器调度或自动回滚。

## 验收标准

- **AC1：工具目录完整**：启动应用后，工具注册表包含全部 21 个新工具，且不包含 `team`、`team_lead`、`team_member`。
- **AC2：Schema 原子化**：逐个读取 21 个工具定义，确认顶层 schema 不包含 `action`/`operation`，不包含跨动作的大型 `oneOf`，并且未知字段被拒绝。
- **AC3：生命周期可用**：执行创建、接管、状态、归档流程，结果和失败条件与现有服务约束一致，持久化数据格式不变。
- **AC4：Lead 编排可用**：Lead 能启动批次、启动/终止成员、创建和管理任务、审批计划、发送关停请求并整合完成批次。
- **AC5：Member 工作流可用**：Member 能领取绑定任务、提交计划、发送状态和普通消息、响应关停请求，并且不能冒用其他成员。
- **AC6：任务并发保护**：使用过期 `expected_revision` 更新、删除、领取或转换任务时，调用失败且 TaskBoard 不产生写入。
- **AC7：角色隔离**：分别以未激活主会话、Lead 和 Member 构造工具列表，结果只包含该角色允许的集合；手工调用隐藏工具得到结构化拒绝。
- **AC8：权限不降级**：在默认、严格、计划和协调器模式下执行代表性读写调用，审批、拒绝、协调器 shell 限制和成员写入审批行为保持现有规则。
- **AC9：中文提示**：检查所有新工具描述、参数描述、权限拒绝和用户可见错误文本，确认均为中文；英文仅保留工具标识、枚举值和 `reason_code`。
- **AC10：迁移与回归**：旧名称出现在配置、Hook 或 Skill 白名单时，启动/加载校验给出中文错误；全量测试、文档检查和至少一个 Lead→Member→整合端到端场景通过。
